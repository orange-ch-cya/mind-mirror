## 三个核心设计哲学

本文档是一份可直接交付开发实施的完整技术需求规格说明书。所有设计决策均基于以下三个核心设计哲学展开，任何开发人员在实现功能时都应首先理解并遵守这些原则：

### 第一原则：简约可拓展

系统架构不做过度设计，但必须为未来扩展预留清晰接口。当前阶段的每一个功能实现，都要保证后续可以在不修改核心代码的情况下进行配置调整、功能新增和性能升级。数据库设计要预留扩展字段，API 设计要遵循版本化管理思路，前端组件要具备可复用性。

### 第二原则：以患者为中心

患者是本平台最需要保护的群体。患者端的所有交互设计、文案呈现、数据展示，都必须遵循「不伤害、不标签、不引导自我诊断」的底线。给患者看的内容要温暖、笼统、充满人文关怀；给医生和家长看的内容则必须专业、详尽、具备临床参考价值。

### 第三原则：双重读者适配

医生端报告的专业深度要足够支撑临床辅助判断，但同时必须控制术语密度，确保有一定教育背景但没有临床心理学训练的专业人士（如学校心理老师、社工、关注孩子心理健康的家长）也能理解报告内容。凡是必须使用的专业术语，都要配以简明易懂的注释说明。

## 措辞约定

本文档中的「必须」「禁止」「应当」「可以」等措辞遵循 **RFC 2119** 标准，分别对应 MUST、MUST NOT、SHOULD、MAY 的含义，开发人员应当严格区分这些要求的强制性级别。

# 第一章 项目概述

## 1.1 项目基本信息

**项目名称**：心镜 · 心理健康自测工具平台

**项目核心定位**：一个免登录、免注册的心理健康自测工具平台。用户通过邀请码完成测评后，数据定向推送给医生或家长，由具备专业资质的人员在线下向患者解读结果。平台自身明确不做诊断，只承担「数据传递」和「状态描述」两个基础功能。

**项目本质定义**：本平台不是医疗工具，不做任何形式的诊断。它是一个专业的数据传递工具，其存在的全部意义可以概括为三个「帮」：帮患者把答题数据安全地传递给医生，帮医生拿到结构化的参考信息，让专业人士在线下、在合适的时候、用合适的方式把结果告诉患者。仅此而已。

## 1.2 目标用户画像

本平台涉及三类用户角色，每类角色的使用场景和需求有本质差异：

**患者端用户**：可能是任何年龄段、任何教育背景、任何心理状态的个体。他们可能正在经历情绪困扰，可能对心理测评有疑虑或恐惧，可能对测试结果有焦虑。因此患者端的交互必须极简、文案必须温暖、绝不能造成二次伤害。患者不注册、不登录、不留名，仅通过邀请码参与测评。

**医生/家长端用户**：包括精神科医生、心理咨询师、学校心理老师、关注孩子心理健康的家长等。他们的共同特点是具备一定专业背景或强烈学习意愿，需要通过平台获取结构化的测评数据，用于辅助线下沟通和判断。医生端需要看到完整的专业数据，家长端需要同样详细但更易理解的数据呈现。

**平台管理员**：负责量表库的维护、常模数据的更新、医生账号的管理、分科规则的配置等工作。管理员需要操作便捷的后台管理界面，无需通过数据库直接操作。

## 1.3 项目边界声明

平台明确不涉及以下功能领域：不提供在线诊断或治疗建议，不替代临床面诊，不进行处方建议，不提供心理咨询服务，不建立医患关系，不存储任何可直接追溯至具体个人的身份信息（姓名、身份证号、手机号、IP 地址等均不采集）。平台所有功能均围绕「数据采集—数据传递—数据呈现」这条主线展开，绝不越界。

## 1.4 技术边界声明

首版不引入人工智能生成内容功能。所有结果显示均基于硬规则引擎驱动。AI 融合功能明确规划在第二迭代阶段，届时将接入 DeepSeek API 生成个性化但安全受控的解释文本。当前阶段需要为 AI 接口预留标准的调用位置和数据结构，但不实现具体调用逻辑。

# 第二章 核心设计理念详解

## 2.1 简约可拓展原则的落地要求

简约不是简陋，可拓展不是预留一堆用不上的抽象层。本项目中「简约可拓展」的具体实现要求如下：

**数据库层面**：核心业务表结构保持稳定，但所有配置类数据（量表条目、计分规则、常模数据、分科规则）必须存储在数据库表中而非硬编码在代码中。新增或修改一个量表不应要求开发人员介入，管理员通过后台界面即可完成。数据库版本控制采用迁移脚本管理，所有 DDL 变更必须可追溯、可回滚。

**API 层面**：所有接口路径以 `/api/v1/` 为前缀，为后续版本升级预留空间。接口设计遵循 RESTful 规范，请求和响应格式统一使用 JSON。每个接口的响应结构包含统一的 `code`、`message`、`data` 三个顶层字段，便于前端统一处理。错误码体系独立于 HTTP 状态码，业务错误统一返回 HTTP 200，通过 `code` 字段区分业务结果。

**前端层面**：组件设计遵循原子设计方法论。基础 UI 组件（按钮、输入框、弹窗、卡片等）作为原子组件独立封装；业务组件（量表答题组件、报告展示组件、邀请码管理组件等）组合原子组件构建；页面级组件承载完整的业务场景。任何组件的修改不应影响其他无关组件。

**配置层面**：所有可变参数（快筛阈值、推送规则、常模数据、分科标签映射、免责声明文案、禁用词列表等）均需实现后台可配置。配置文件或配置表的结构要支持热更新，修改配置后无需重启服务即可生效。

## 2.2 以患者为中心原则的落地要求

「以患者为中心」在本项目中不是一句口号，而是有明确实现标准的工程原则：

**知情权保障**：患者在开始答题前，必须阅读并主动勾选知情同意书。知情同意书的内容必须清晰告知：本平台的性质（非医疗工具）、数据去向（邀请码持有者可见）、患者自身的权限（无法自行查看详细报告）、撤回权利（24 小时内可撤回）。知情同意的勾选记录作为数据归属的追溯凭证永久保存。

**隐私保护**：患者端不采集任何个人身份信息。不要求输入姓名、手机号、邮箱、身份证号等可识别字段。不采集 GPS 定位。不读取设备信息。不埋设第三方跟踪脚本。邀请码是关联患者数据的唯一标识，而邀请码本身由医生生成和管理，与患者个人身份无直接映射关系。

**情绪安全**：患者看到的结果页不显示任何分数、量表名称、倾向性词汇、科室建议。仅显示温和的结束语、通用性的鼓励话语、普适性的心理调节小贴士、固定的免责声明、以及「请联系邀请您参与测评的人士获取进一步解读」的提示。整个体验应该让患者感觉「完成了一件有意义的事」，而非「被贴上了一个标签」。

**撤回权保障**：患者在提交测评后的 24 小时内，拥有无条件撤回数据的权利。撤回操作将导致其测评数据从数据库中彻底删除，关联的邀请码同步作废。撤回功能在患者端结果页提供明确的入口，操作步骤简单明了，不需要任何审批流程。

**不伤害底线**：平台全链路杜绝标签效应。禁用词表内置在系统中，不仅约束前端显示文案，也约束后台配置时的录入校验。凡是可能让患者产生「我被诊断为 XX」联想的表述，一律替换为客观状态描述。这一要求在结果生成逻辑中以硬编码校验层实现，不依赖人工遵守。

## 2.3 双重读者适配原则的落地要求

医生/家长端的报告呈现面临一个核心矛盾：专业用户需要精确的数据，非专业用户需要能理解的解读。解决方案是分层呈现：

**数据层**：所有读者看到相同的原始数据。包括逐题作答记录、各量表原始分数、与常模的对比数据、分科参考标签。这层数据保持客观、完整、不修饰。

**解读层**：为专业数据配发通俗注释。例如在「GAD-7 总分 12 分」旁边显示注释「该分数处于中度焦虑范围（常模参考：0-4 分正常，5-9 分轻度，10-14 分中度，15-21 分重度）」。注释文案由专业人士预先编写，存储在配置库中，系统根据分数区间自动匹配，不依赖 AI 实时生成。

**建议层**：分科标签使用双轨描述。面向医生的描述可以简洁专业（如「建议精神科进一步评估」），面向家长的描述需要更多上下文（如「孩子的情绪状态显示出一些需要关注的特征，建议您带孩子前往医院的临床心理科或精神科，由医生进行全面评估。这个建议不意味着孩子一定有问题，只是表明目前的状态值得专业人士的关注。」）。两套描述在配置中成对存储，报告展示时根据查看者角色自动选择，或者同时显示并以标签区分。

# 第三章 患者端功能详细设计

## 3.1 首页设计

患者端首页是整个用户体验的起点。页面设计必须传达安全、信任、简洁的感受。

**页面结构**：从上到下依次为：平台名称与 Logo 区域、一句话介绍语、量表简介卡片、邀请码输入区域、匿名自测入口按钮、底部固定版权声明和来源标注。

**平台名称与 Logo**：显示「心镜」二字，字体采用圆体或无衬线体的柔和变体，颜色使用暖色调但不过分活泼。Logo 设计为抽象的镜像或水面倒影意象，传递「看见自己」而非「被审视」的感觉。该区域固定于页面顶部，滚动时不隐藏。

**一句话介绍语**：「了解近期的心理状态，从一个简单的自我觉察开始。」这句话需要让首次访问的用户立即理解平台的性质和目的，用词柔和、不制造压力、不暗示问题。

**量表简介卡片**：使用折叠面板的形式，默认展示一张简短说明卡片，内容为：「本平台提供标准化的心理状态自我评估工具。您将在专业人士的邀请下完成一份或多份问卷，您填写的内容将安全地传递给邀请您的人士，由他们在适当的时候与您沟通。」卡片内可以有一个「了解更多」的展开按钮，展开后显示更详细的平台介绍、数据去向说明、隐私保护承诺等内容。

**邀请码输入区域**：这是首页最核心的功能区域。设计为一个视觉突出的输入框组合：一个文本输入框（placeholder 提示「请输入邀请码」）、一个「开始测评」按钮。输入框和按钮的尺寸要足够大，适配移动端拇指操作。输入框支持粘贴功能。按钮在未输入邀请码时置灰不可点击，输入内容后激活为主色调。

**匿名自测入口**：这是一个次要入口，设计为文字链接或边框按钮样式，文案为「我没有邀请码，想先了解一下」。点击后进入一个说明页面，告知用户匿名自测的功能限制（没有邀请码无法将结果发送给专业人士），引导其联系医生或家长获取邀请码。该入口的存在主要是为了应对用户直接访问链接但没有邀请码的情况，避免产生死胡同体验。

**底部固定区域**：显示版权声明「本平台量表来源于《心理量表自评手册》（198X 年版）及其他公开学术资源，仅供学习参考使用。如有版权疑虑请联系我们。」以及平台的技术支持信息。该信息字号较小，颜色为次级文本色，不干扰主要操作区域。

## 3.2 知情同意流程

知情同意是本平台最重要的合规设计之一，也是数据归属追溯的法律凭证。该流程必须设计为不可跳过的强制步骤。

**触发时机**：用户在首页输入有效邀请码并点击「开始测评」后，首先进入知情同意页面，而非直接开始答题。匿名自测入口如果未来开放功能，同样需要经过知情同意页面。

**页面内容**：知情同意书全文以清晰易读的字号和行距呈现。内容包含以下核心要点，文案需要经过法律专业人士审定：

- 本平台的性质声明：非医疗工具，测试结果不代表临床诊断，不能替代专业医生的面诊评估。
- 数据去向说明：您填写的所有答题数据将发送给向您提供邀请码的人士（可能是医生、心理咨询师、学校老师或家长）。平台运营方不查看、不使用您的个人数据。
- 患者知情权说明：您本人无法在本平台查看详细的分数和报告，这是平台的有意设计，以避免未经专业解读的数字对您造成不必要的困扰。详细结果将由向您提供邀请码的人士在线下以适当的方式与您沟通。
- 撤回权说明：您有权在提交测评后的 24 小时内撤回数据。撤回后数据将被彻底删除，邀请码作废。撤回操作可在结果页面找到入口。
- 自愿参与声明：您完全自愿参与本次测评，可以随时停止作答并离开页面，未提交的数据不会被保存。

**操作设计**：知情同意书内容下方设置一个复选框，文案为「我已认真阅读并理解以上内容，同意参与测评」。复选框默认未勾选。复选框下方有一个「开始答题」按钮，在复选框未勾选时置灰不可点击，勾选后激活。页面底部还有一个「返回」按钮，允许用户选择不同意并退出。

**记录机制**：用户勾选同意并点击开始答题时，后端记录一条知情同意记录。记录内容包括：邀请码、同意的时间戳（精确到秒）、同意时的用户代理字符串（用于证明是真人操作）、同意的 IP 地址哈希值（不存储原始 IP，仅存储不可逆哈希值用于防篡改验证）。该记录与测评数据绑定存储，作为数据归属和用户知情权的追溯凭证。

## 3.3 快速筛查流程

快速筛查是整个测评流程的第一层分流机制，使用 PHQ-4 量表（4 道题），预计完成时间 1 分钟。

**量表说明**：PHQ-4（Patient Health Questionnaire-4）是经过广泛验证的超简短心理状态筛查工具，包含 4 道题目，其中前 2 题测量焦虑维度，后 2 题测量抑郁维度。每题采用 4 级评分（0=完全没有，1=有几天，2=一半以上天数，3=几乎每天），总分范围 0-12 分。该量表以其简洁性和良好的筛查效能，非常适合作为本平台的入口筛查工具。

**页面设计**：快速筛查页面以一张一张卡片的形式呈现题目，每次只显示一道题，用户选择答案后自动滑入下一题。这种单题呈现的设计可以降低用户的认知负荷，避免看到 4 道题同时出现时产生的「做问卷」压力感。

**题目文案**：

- 第 1 题（焦虑维度）：在过去两周中，您是否经常感到紧张、焦虑或不安？
- 第 2 题（焦虑维度）：在过去两周中，您是否经常无法停止或控制担忧？
- 第 3 题（抑郁维度）：在过去两周中，您是否经常对事情缺乏兴趣或乐趣？
- 第 4 题（抑郁维度）：在过去两周中，您是否经常感到情绪低落、沮丧或绝望？

**选项设计**：每道题的四个选项以纵向排列的大尺寸按钮呈现，按钮上显示选项文字和对应的简短说明：

- 完全没有（0 分）- 从未出现
- 有几天（1 分）- 偶尔出现，但不多
- 一半以上天数（2 分）- 经常出现，多数日子都有
- 几乎每天（3 分）- 几乎每天都出现

按钮选中后高亮显示，同时自动推进到下一题。为了给用户反应时间，自动推进设置 300 毫秒的短暂延迟，让用户能看到自己的选择被确认后再切换题目。

**进度指示**：页面顶部显示一个细长的进度条，4 道题对应 4 个等分段。进度条填充使用柔和的渐变色，不显示数字百分比（避免「还剩下 25%」这种催促感），仅在视觉上让用户感知进度。

**防误触设计**：不支持浏览器后退按钮返回修改已答题目（这是有意设计，减少用户在快筛阶段的纠结和反复修改）。但如果用户在 PHQ-4 阶段退出，下次重新进入需要重新作答（因为 PHQ-4 数据在推送深度包之前不会持久化存储，这是隐私保护的设计）。

**完成后过渡**：4 道题全部作答完毕后，页面显示一个简短的过渡动画（2-3 秒），动画内容为柔和的渐变波纹或呼吸光效，配合一句「正在整理您的情况...」的过渡文案。这个短暂的等待时间实际上用于后端进行分数计算和深度包匹配，但在用户感知上是一个自然的处理间隔，而非生硬的加载等待。

## 3.4 智能推送机制

快速筛查完成后，系统根据 PHQ-4 的得分自动决定下一步的流程走向。这是本平台核心的「智能分流」逻辑。

**推送决策流程**：系统在后端对 PHQ-4 的总分和两个维度分（焦虑维度=前 2 题总分，抑郁维度=后 2 题总分）分别进行判断，按照以下决策树匹配对应的深度包：

**分支一：焦虑倾向明显**

- 触发条件：焦虑维度得分 ≥4 分，且抑郁维度得分 <3 分。
- 推送内容：焦虑深度包，包含 GAD-7（广泛性焦虑障碍量表，7 题）、SAS（焦虑自评量表，20 题）、HADS-A（医院焦虑抑郁量表-焦虑分量表，7 题）。
- 推送逻辑说明：当用户主要表现为焦虑症状而抑郁症状不明显时，推送三个从不同角度评估焦虑的量表，实现交叉验证。GAD-7 关注近两周的焦虑症状频率，SAS 关注更广泛的焦虑体验，HADS-A 从医院筛查视角评估焦虑水平。

**分支二：抑郁倾向明显**

- 触发条件：抑郁维度得分 ≥4 分，且焦虑维度得分 <3 分。
- 推送内容：抑郁深度包，包含 PHQ-9（患者健康问卷抑郁量表，9 题）、SDS（抑郁自评量表，20 题）、HADS-D（医院焦虑抑郁量表-抑郁分量表，7 题）。
- 推送逻辑说明：三个量表同样实现交叉验证。PHQ-9 与 PHQ-4 同源但题目更详细，SDS 是经典的抑郁自评工具，HADS-D 提供医院筛查视角。

**分支三：焦虑与抑郁均偏高**

- 触发条件：焦虑维度得分 ≥4 分，且抑郁维度得分 ≥4 分。
- 推送内容：情绪综合包，包含 GAD-7（7 题）、PHQ-9（9 题）、HADS（完整版 14 题，含焦虑和抑郁两个分量表）、SCL-90 精简版（约 30 题版本，覆盖躯体化、强迫、人际敏感、抑郁、焦虑、敌对、恐怖、偏执、精神病性等维度）。
- 推送逻辑说明：当焦虑和抑郁症状同时明显时，需要更全面的评估。HADS 完整版可以同时评估两个维度，SCL-90 精简版提供多维度视角，帮助识别可能存在的其他伴随症状。

**分支四：睡眠问题突出**

- 触发条件：PHQ-4 总分 <6 分（未达前三个分支的阈值），但系统需要额外判断。由于 PHQ-4 不直接测量睡眠，此分支的触发需要依赖一个补充逻辑：在 PHQ-4 完成后增加一道额外的睡眠筛查题「在过去两周中，您是否经常遇到睡眠问题（如入睡困难、睡眠浅、早醒等）？」如果用户选择「一半以上天数」或「几乎每天」，则触发睡眠分支。
- 推送内容：睡眠专项包，包含 PSQI（匹兹堡睡眠质量指数，19 题自评部分）、ESS（爱泼沃斯嗜睡量表，8 题）。
- 推送逻辑说明：睡眠问题往往是情绪问题的伴随症状，也可能是独立的主诉。对于 PHQ-4 得分不高但睡眠困扰明显的用户，推送专门的睡眠评估工具，避免遗漏。

**分支五：整体偏高（非特异性困扰）**

- 触发条件：PHQ-4 总分 ≥6 分，但不满足分支一或分支二的特异性条件（即两个维度分数都介于 3-4 分之间，没有哪个维度特别突出）。
- 推送内容：全面筛查包，包含 SCL-90 标准版（90 题，覆盖 10 个症状维度）。
- 推送逻辑说明：当用户报告了中等程度的困扰但无明显偏向时，使用最全面的自评工具进行广泛筛查，帮助发现用户自己可能未意识到的症状维度。

**分支六：压力相关问题**

- 触发条件：在 PHQ-4 完成后增加一道补充筛查题「在过去一个月中，您是否经历了重大压力事件（如工作/学业压力、人际关系冲突、重大变故等）？」如果用户选择肯定回答，且 PHQ-4 总分 <6 分，触发压力分支。
- 推送内容：压力应激包，包含 PSS（压力知觉量表，10 题或 14 题版本）、IES-R（事件影响量表修订版，22 题）。
- 推送逻辑说明：为近期经历压力事件但情绪症状尚不明显的用户提供压力专项评估。

**分支七：分数正常（无需深度测评）**

- 触发条件：PHQ-4 总分 ≤2 分（焦虑维度 ≤1 且抑郁维度 ≤1），且睡眠和压力补充筛查题均为否定回答。
- 推送内容：不推送任何深度量表。系统生成一个轻量级的「状态良好」结果页。
- 处理逻辑：用户直接跳转到患者版结果页，显示鼓励和肯定的话语，以及日常心理健康维护小贴士。流程到此结束。

**推送规则的存储与配置**：所有推送规则（包括 PHQ-4 阈值、补充筛查题的触发条件和答案映射、各分支对应的量表组合包）均存储在数据库的配置表中，不允许硬编码在业务逻辑中。管理员可以通过后台修改阈值、调整量表组合包的内容，修改后立即生效。配置表的结构将在数据库设计章节详细说明。

**过渡体验设计**：推送决策完成后，系统向患者展示一个确认弹窗，内容为：「根据您刚才的快速筛查，系统为您准备了一套更详细的问卷，大约需要 X 分钟完成。这将帮助邀请您的人士更全面地了解您的情况。请认真作答，您的每一道回答都很重要。」弹窗中明确告知预计用时，并有一个「开始答题」按钮。用户点击后进入深度量表的作答流程。

## 3.5 量表作答流程

深度量表的作答流程是平台的核心交互，需要在大规模题目（某些组合包可能包含超过 100 道题）的情况下保持良好的用户体验，同时确保数据质量。

**题目呈现方式**：所有题目以单题逐页呈现。每页包含：当前题目的题干、选项按钮组、上一题/下一题导航（部分场景需要）、页面顶部的量表名称和总进度条、当前题目在该量表内的序号（如「第 3 题/共 20 题」）。

**进度条设计**：如果推送的组合包包含多个量表，顶部进度条显示的是整个作答流程的总进度。例如「焦虑深度包」包含 GAD-7（7 题）+ SAS（20 题）+ HADS-A（7 题）= 34 题，进度条总长度为 34 段。两个量表之间有一个短暂的「休息页」，显示「第一部分已完成，即将开始下一部分」，用户可以在此暂停一下（但已作答的数据已经暂存）。

**选项交互设计**：所有量表选项统一采用大尺寸的纵向排列按钮。选项文字根据量表原始设计显示（可能是频次描述如「没有/有时/经常/总是」，也可能是程度描述如「完全不符合/比较不符合/比较符合/完全符合」，或者是严重程度如「无/轻度/中度/重度/极重度」）。每个选项被点击后高亮显示为选中态，同时自动前进到下一题，延迟 300 毫秒。如果用户希望取消选择，可以在 300 毫秒内点击另一个选项来替换选择（但这在逻辑上是直接修改了答案，题目不倒退）。

**导航设计**：默认情况下，用户选择答案后自动前进，不显示「上一题」按钮。这个设计选择需要说明理由：在心理测评中，「不允许回退修改」有助于获得更真实的直觉反应，减少反复斟酌带来的社会期许效应。但在每个量表的最后一题提交前，系统会显示一个确认页，列出该量表所有题目的答案摘要，用户可以在这里看到自己的全部选择，如果需要修改可以点击某题返回。这个设计平衡了「减少中途反复修改」和「允许最终检查确认」两个需求。

**必填约束**：所有题目均为必填，不支持跳过。如果用户在确认页发现漏题（理论上不会出现，因为每题选择后自动前进），系统会标红提示。

**作答数据暂存**：用户在作答过程中，每完成一道题，答案立即通过异步请求发送到后端暂存。这样即使用户中途关闭浏览器或网络中断，已作答的数据不会丢失。暂存的数据标记为「未完成」状态，邀请码不会被锁定。用户下次使用同一邀请码进入时，系统检测到未完成的作答记录，询问用户「检测到您有未完成的测评，是否继续上次的进度？」用户可以选择继续或重新开始。

**中断与恢复机制**：如果用户在作答过程中超过 30 分钟没有任何操作（计时逻辑在前端实现，每道题选择后重置计时器），系统弹出提示「您已停留较长时间，需要继续作答吗？」，如果用户在提示后 2 分钟内仍无操作，当前作答进度自动保存，页面显示「作答已暂停，您可以在 24 小时内使用相同的邀请码继续完成测评。超时未完成的数据将被清除。」这个设计考虑了用户在手机上作答时可能被打断的实际情况。

**量表间过渡**：当用户完成组合包中一个量表的所有题目并在确认页提交后，如果后续还有量表，系统显示过渡页。过渡页内容为：「您已完成[量表名称]的作答。接下来是[下一个量表名称]，预计需要 X 分钟。请稍作休息，准备好后点击继续。」过渡页的存在给了用户心理上的分段感，避免了「做完一套又来一套」的疲惫感。过渡页上可以显示一个简单的深呼吸引导动画（吸气 4 秒-屏住 4 秒-呼气 6 秒的节奏圆环动画），这个设计体现了对用户情绪状态的关怀。

**全部完成后提交**：当组合包中所有量表都已完成，系统显示最终确认页，列出本次测评包含的所有量表名称和题目数量，以及一个总体的「确认提交」按钮。按钮上方有一段提示文字：「您已完成所有题目。点击提交后，您的答题数据将发送给邀请您的人士。提交后 24 小时内您可以撤回数据。请确认您的作答是认真和真实的。」用户点击确认提交后，所有暂存的数据状态变更为「已完成」，邀请码状态变更为「已使用」，数据归属关系正式建立。

**防重复提交**：提交按钮点击后立即置灰并显示「提交中...」，后端通过邀请码的唯一性约束确保不会产生重复提交。如果用户在提交过程中网络中断，前端会持续重试直到收到后端的成功响应。

## 3.6 患者版结果页

患者版结果页是本平台「以患者为中心」理念的最集中体现。该页面必须严格过滤所有可能引起不当联想的信息，仅呈现安全、支持性的内容。

**页面结构**：从上到下依次为：温和的结束语、鼓励话语、通用心理调节小贴士、固定免责声明、联系邀请人提示、撤回数据入口、底部版权信息。

**温和的结束语**：这是一句或一小段话，用来肯定用户完成测评的行为。文案示例：「感谢您的认真参与。自我觉察是关爱自己的第一步。您愿意花时间了解自己的状态，这件事本身就值得肯定。」这句话应该让用户感到被尊重和被鼓励，而不是「完成了任务」的感觉。文案内容存储在配置表中，管理员可以根据需要调整优化。

**鼓励话语**：多组鼓励性的话语，每次随机抽取一组展示，或者根据时间段变化（比如晚上显示「今晚请给自己一个温柔的拥抱」）。示例文案：

- 「心理健康和身体健康一样重要，您今天的关注是对自己的善待。」
- 「每个人的情绪都会有起伏，这完全正常，您不是一个人在面对。」
- 「请记得，寻求帮助不是软弱，而是一种力量和智慧的体现。」

**通用心理调节小贴士**：提供 3-5 条简单、实用、无专业门槛的自我调节建议。这些建议需要经过心理学专业人士审核，确保安全有效、不会对任何特定心理问题产生误导。示例内容：

- 规律作息：尽量保持固定的睡眠和起床时间，身体的节律对情绪有直接影响。
- 适度运动：每天 20-30 分钟的快走或伸展，不需要高强度运动，动起来就是好的开始。
- 正念呼吸：感到紧张时，试试 4-7-8 呼吸法——用鼻子吸气 4 秒，屏住呼吸 7 秒，用嘴巴缓慢呼气 8 秒，重复几次。
- 社交联结：和信任的人聊聊天，哪怕只是分享日常，人际联结是情绪缓冲的重要资源。
- 减少信息过载：适当减少刷手机的时间，特别是睡前，给大脑留一些安静的空间。

**固定免责声明**：该声明固定出现在结果页，不可由管理员关闭或修改（硬编码保证）。文案如下：

- 「本结果仅反映您近期填写问卷时的心理状态倾向，不代表临床诊断。」
- 「心理健康是动态变化的，本次结果仅代表您作答期间的自我感受。」
- 「如您近期持续感到困扰或不适，强烈建议前往正规医院精神科/临床心理科就诊咨询。」
- 「如需心理支持，在中国大陆可拨打全国统一心理援助热线 12356；遇到紧急危险请立即联系当地急救服务。」

> 注：12356 已由国家卫健委确认为全国统一心理援助热线，具体服务时间以当地接线服务为准。

**联系邀请人提示**：明确告知用户如何获取详细结果。文案：「您的完整测评数据已安全地发送给向您提供邀请码的人士。如需了解详细结果和专业解读，请直接联系邀请您参与测评的人士。出于对您的保护，平台不会直接向您展示分数和详细报告。」如果需要，这里可以放一个「唤起微信/短信联系邀请人」的按钮，但由于平台不存储用户联系方式，这个功能只能通过系统级分享接口实现（且需要用户主动操作），或者仅提供文案引导。

**撤回数据入口**：在结果页底部设置一个不显眼但不隐蔽的「撤回我的数据」按钮或链接。点击后进入撤回确认流程（详见 3.7 节）。该按钮在提交后的 24 小时内显示，超过 24 小时后自动消失。按钮样式设计为次要按钮（边框按钮或文字链接），不采用红色等警示色，避免让用户产生「我的数据很危险」的负面联想。按钮文案：「我需要撤回我的测评数据」。

## 3.7 数据撤回功能

24 小时撤回机制是患者权益的重要保障。该功能需要在技术和体验上都做到简洁可靠。

**撤回触发**：患者在结果页点击「撤回我的数据」按钮，进入撤回确认页面。

**撤回确认页面**：该页面需要再次进行知情告知，内容包括：

- 撤回的后果说明：「撤回后，您的所有答题数据将被从系统中彻底删除，无法恢复。您使用的邀请码将作废，邀请您的人士将无法查看或找回这些数据。」
- 再次确认：「您确定要撤回吗？此操作不可撤销。」
- 确认操作：提供一个输入框，要求用户输入「确认撤回」四个字，然后点击「确认撤回」按钮。这个二次确认机制防止误操作。

**撤回执行**：用户确认撤回后，后端执行以下操作：

1. 验证当前时间距离数据提交时间是否在 24 小时内。超过 24 小时则拒绝撤回，返回提示「已超过 24 小时撤回期限」。
2. 验证邀请码状态是否为「已填」。只有「已填」状态的数据可以撤回（已被医生标记为「已阅」的数据同样可以撤回，阅取状态不影响患者的撤回权）。
3. 将该邀请码关联的所有答题数据（包括知情同意记录、量表作答记录、分数记录）从数据库中物理删除。注意是 DELETE 而非软删除标记，确保数据不可恢复。
4. 邀请码状态更新为「已撤回」。
5. 返回撤回成功响应。

**撤回后展示**：撤回成功后，患者端页面显示：「您的数据已成功撤回并删除。邀请码已作废。如需重新测评，请联系邀请您的人士获取新的邀请码。感谢您的参与，祝您一切安好。」页面上不再显示任何数据相关的信息。

**撤回记录**：系统中保留一条匿名化的撤回记录，仅包含：邀请码（作废状态）、撤回时间戳、操作来源（患者端），不关联任何答题内容。这条记录用于统计和审计目的，不包含任何可追溯至具体个人的信息。

**边界情况处理**：

- 同一邀请码重复撤回请求：返回「该数据已被撤回」提示。
- 邀请码未使用（状态为「未使用」）的撤回请求：返回「该邀请码尚未使用，无需撤回」。
- 邀请码已被另一份数据使用（虽然业务逻辑保证了唯一性，但防御性编程仍需要处理）：返回错误提示。

# 第四章 医生/家长端功能详细设计

## 4.1 账号体系与登录验证

医生/家长端的用户是平台的核心服务对象之一。他们通过查看测评数据，在线下为患者提供专业解读。

**账号创建方式**：账号由平台管理员在管理后台手动创建，不开放自主注册。这样设计的原因是：平台的数据涉及敏感的心理健康信息，需要管理员对使用者身份进行基本把控。创建账号时需要填写：登录用户名、初始密码（首次登录强制修改）、使用者姓名或机构名称（可选）、账号角色（医生/家长/其他）、账号状态（启用/停用）。

**登录页面设计**：登录页面极简设计。包含用户名输入框、密码输入框、登录按钮、以及「忘记密码」链接（触发管理员重置密码的工作流）。页面无注册入口。背景色采用专业沉稳的色调，区别于患者端的温暖色调，暗示这是专业人士的工作区。

**登录验证逻辑**：

- 用户提交用户名和密码后，后端进行验证。
- 密码使用 bcrypt 或 argon2 算法进行哈希存储和比对，严禁明文存储。
- 连续 5 次登录失败后，该账号锁定 30 分钟，防止暴力破解。
- 登录成功后，后端生成 JWT（JSON Web Token），包含用户 ID、角色、过期时间（建议 24 小时），返回给前端。
- 前端将 JWT 存储在 localStorage 或 httpOnly cookie 中（安全起见推荐 httpOnly cookie + CSRF token 方案），后续所有 API 请求在 Authorization 头中携带该 token。

**会话管理**：

- JWT 过期后需要重新登录。
- 支持主动登出，登出时前端清除 token。
- 单账号单设备登录（可选，初期可放宽为多设备登录以方便使用）。

**首次登录强制修改密码**：创建账号时设置的初始密码为临时密码。用户首次登录时，系统检测密码是否为初始状态（可以通过密码最后修改时间字段判断，初始创建时该字段为 NULL），如果是则跳转到修改密码页面，强制修改密码后才能进入系统。新密码要求：长度不少于 8 位，包含字母和数字。

## 4.2 邀请码管理系统

邀请码是连接患者数据与医生/家长权限的唯一凭证，其管理是医生端最核心的功能。

**邀请码生成**：

- 医生登录后在「邀请码管理」页面点击「生成邀请码」按钮。
- 系统即时生成一个唯一的邀请码。邀请码格式建议：8 位字母数字混合，排除容易混淆的字符（0/O、1/I/L），保证大小写不敏感（统一存储为大写或小写）。例如：A3B7K9M2。
- 邀请码生成后立即显示在页面上，并提供「复制」按钮。同时可以生成一个包含邀请码链接的二维码，方便患者扫码直接进入答题页面（二维码编码的 URL 为：https://平台域名/patient?code=A3B7K9M2）。
- 邀请码生成时记录：邀请码内容、生成医生 ID、生成时间、状态（初始为「未使用」）、备注（可选，医生可以填写此码对应的患者称呼或用途，如「周三门诊张同学」。注意：此处填写的信息不应包含患者真实全名，系统需要提示医生注意隐私保护，或者将此字段限制为非必填且做脱敏提醒）。

**邀请码列表与状态管理**：

- 邀请码管理页面以列表形式展示当前登录医生生成的所有邀请码。
- 列表字段：邀请码、生成时间、状态、备注、操作。
- 状态标识使用不同颜色区分：
  - 未使用（灰色或蓝色）：邀请码已生成，患者尚未使用。
  - 已填（橙色）：患者已完成测评，医生尚未查看报告。
  - 已阅（绿色）：医生已查看过报告。
  - 已撤回（红色）：患者在 24 小时内撤回了数据。
  - 已过期（如果实现了有效期功能，灰色）：邀请码超过有效期未被使用。
- 操作按钮根据状态动态显示：
  - 未使用：查看二维码、复制链接、作废（手动作废邀请码）、编辑备注。
  - 已填：查看报告。
  - 已阅：查看报告。
  - 已撤回：查看撤回记录（仅能看到撤回时间和状态，看不到原始数据）。
- 支持按状态筛选和按生成时间排序。

**邀请码唯一性与安全性**：

- 邀请码在系统全局唯一，不同医生生成的邀请码不会重复。
- 邀请码仅限生成该码的医生查看其关联的数据。其他医生即使知道邀请码内容，也无法在系统中查看不属于他们的数据（权限校验在后端严格实施）。
- 邀请码生成算法需要保证足够的随机性（使用密码学安全的随机数生成器），避免被推测或枚举。

**邀请码链接跳转逻辑**：

- 患者扫描二维码或点击链接后，跳转到患者端首页，URL 参数中的邀请码自动填充到输入框中。
- 如果邀请码已过期或无效（已使用、已撤回、不存在），首页显示友好提示：「该邀请码无效或已使用，请联系向您提供邀请码的人士获取新的邀请码。」

## 4.3 报告查看功能

报告查看是医生/家长端价值实现的核心环节。报告需要在「专业详尽」和「家长可理解」之间取得平衡。

**报告入口**：从邀请码列表的「查看报告」按钮进入，或从「报告列表」统一入口查看所有已填和已阅的报告。

**报告页面整体布局**：采用左右分栏或上下分区的响应式布局（PC 端左右分栏，移动端上下堆叠）。左侧/上方为导航区，列出报告中包含的量表名称，点击可快速跳转到对应量表的详细内容。右侧/下方为主内容区，滚动展示完整报告。

**报告内容结构（从上到下）**：

**第一部分：报告概览**

- 邀请码和备注信息（医生自己填写的备注）。
- 测评完成时间。
- 知情同意状态：患者是否勾选了知情同意书，勾选时间。
- 使用的量表组合包名称（如「焦虑深度包」）。
- 一个总览表格，列出所有施测量表的名称、原始总分、常模参考范围简表。

**第二部分：逐量表详细报告**

每个量表独立一个区块，包含以下子内容：

- 量表名称（中文全称+英文缩写，如「广泛性焦虑障碍量表 GAD-7」）。
- 量表简介：一段简短的说明文字，介绍该量表测量什么、有多少题、评分范围、以及权威来源。这段简介对非专业用户（家长）非常有帮助，让他们理解接下来看到的数字意味着什么。
- 逐题作答记录：以表格形式展示，列为「题号、题目内容、患者选择、对应分数」。患者选择的文字高亮显示。这个表格让专业人士可以逐题审视患者的作答模式，发现需要线下深入讨论的具体问题。
- 维度得分（如适用）：如果量表包含多个维度，展示各维度得分及与常模的对比。例如 HADS 包含焦虑和抑郁两个分量表，SCL-90 包含 10 个因子，PSQI 包含 7 个成分。每个维度分数以进度条或仪表盘形式可视化呈现，同时标注常模参考范围。
- 总分与常模对比：显著展示该量表的总分，并附上与常模数据的对比。常模对比可以设计为：显示患者分数在常模分布中所处的位置（如「高于 80% 的同龄人群」「处于中等偏高水平」），同时显示常模的分级参考（如正常/轻度/中度/重度阈值）。所有对比表述使用描述性语言，避免「异常」「不正常」等标签化表述，改为「偏高范围」「需要关注的水平」等。
- 分科参考标签：如果该量表的分数匹配了分科规则，显示对应的分科标签。标签分为「医生版简短描述」和「家长版详细描述」，根据当前登录用户的角色优先显示对应版本（医生账号看简短版，家长账号看详细版）。两个版本都存储在数据库中，管理员可以切换查看。标签样式设计为带图标的提示卡片，而非警示弹窗，传达「建议参考」而非「判定结论」的语意。

**第三部分：综合分科参考**

如果患者完成了多个量表，系统根据各量表得分的组合情况，生成一个综合性的分科参考建议。这个综合建议由硬规则引擎根据预先配置的规则组合生成。例如：「GAD-7 中度 + PHQ-9 中度 + PSQI 睡眠质量差」的组合可能触发「建议综合评估情绪与睡眠问题」的综合标签。综合建议展示在报告最后，以汇总卡片形式呈现。

**第四部分：报告尾部固定信息**

- 免责声明（硬编码，与患者端一致）：「本报告基于患者自评量表数据生成，仅反映患者作答期间的主观感受，不代表临床诊断。量表的任何分数或分科建议仅供专业人士参考，请结合临床面诊进行综合判断。」
- 报告生成时间戳。
- 平台版权信息。

**报告查看后的状态更新**：医生首次打开某份报告时，对应邀请码的状态自动从「已填」更新为「已阅」。这个状态更新用于帮助医生追踪哪些报告已经处理过。更新是自动的（打开即标记），不需要手动点击「标记已阅」按钮，减少操作步骤。

## 4.4 数据导出功能

医生需要能够将报告导出为可离线阅读或打印的格式，用于存档或线下讨论。

**导出格式支持**：

- PDF 导出：适合打印和正式存档。排版精美，带有平台 Logo 和报告标题。
- Excel 导出：适合数据分析。包含原始数据格式，每个量表的每题得分、维度得分、总分，以结构化表格形式呈现，方便医生进行进一步的数据处理或图表制作。

**PDF 导出设计**：

- 封面页：包含平台 Logo、报告标题（「心理状态自测报告」）、邀请码备注（如有）、测评日期、导出日期、生成机构信息。
- 内容页：按照报告查看的相同结构呈现，保持与在线报告一致的排版和层级。
- 页脚：每页页脚显示免责声明摘要和页码。
- 导出按钮：在报告查看页面的顶部或底部提供「导出 PDF」和「导出 Excel」按钮。点击后后端生成文件并触发下载。文件生成可能需要几秒钟，期间显示加载状态。

**Excel 导出设计**：

- 第一个工作表「概览」：包含患者的基本测评信息（邀请码、测评时间、各量表名称和总分）。
- 后续每个量表独立一个工作表：工作表名称为量表缩写（如 GAD-7）。每个工作表包含：题号、题目完整文本、患者得分、可选范围、常模参考值（如有）。
- 最后一个工作表「原始数据」：以规范化的数据格式列出所有数据，每行一条作答记录，字段包括：量表名称、题号、题目文本、患者得分、维度归属（如适用）。

**导出权限与安全**：导出操作仅限该数据归属的医生账号执行。后端需要在导出接口中进行权限校验。导出的文件不在服务器端留存，生成后即时返回客户端并删除临时文件。文件不包含患者个人身份信息（因为系统本身就不采集）。

## 4.5 知情记录查看

每一次知情同意的勾选都是重要的追溯凭证。医生端需要能够查看这些记录。

**知情记录入口**：在报告详情页的「报告概览」区域，醒目位置显示「知情同意状态：已签署（签署时间：YYYY-MM-DD HH:MM:SS）」。点击该状态文字可展开查看知情同意书的完整文本内容，以及签署时的相关信息（时间戳、用户代理摘要）。

**知情记录的法律意义**：该记录证明患者在答题前已被明确告知数据的去向和使用方式，且主动选择了同意。在出现数据隐私相关争议时，这份记录是平台和医生的重要保护。系统需要确保这些记录不可篡改、不可删除（除了随患者 24 小时撤回而删除）。

# 第五章 管理端功能详细设计

## 5.1 管理员账号与权限

管理端是平台的最高权限区域，用于维护平台的核心配置数据。

**管理员账号**：系统预设一个超级管理员账号，由开发者在系统初始化时创建。超级管理员可以创建其他管理员账号（如需要多人管理）。管理员登录同样使用用户名密码+JWT 方案。管理端登录页面与医生端登录页面分开，使用不同的 URL 路径（如 /admin/login），避免混淆。

**权限模型**：初期采用简单的「超级管理员-普通管理员」两级权限。超级管理员拥有所有权限，普通管理员可以操作量表库和查看日志，但不能管理其他管理员账号。后续如权限需求复杂化，可以扩展为 RBAC 模型，但 MVP 阶段保持简单。

## 5.2 量表库管理

量表库管理是管理端最核心也最复杂的功能。需要支持完整的量表生命周期管理。

**量表列表页面**：

- 以分页表格形式展示所有已录入的量表。
- 列表字段：量表 ID、中文名称、英文缩写、题目数量、适用人群、状态（启用/停用）、最后修改时间、操作按钮。
- 操作按钮：编辑、预览、停用/启用、删除（软删除）。
- 支持按名称搜索、按状态筛选、按适用人群筛选。
- 「新增量表」按钮位于列表上方显著位置。

**量表基本信息编辑**：

点击「新增」或「编辑」进入量表编辑页面，包含以下字段：

- 量表中文名称（必填）：如「患者健康问卷抑郁量表」。
- 量表英文缩写（必填）：如「PHQ-9」。
- 量表来源（必填）：如「来源于《心理量表自评手册》（198X 年版），版权归原作者所有」。
- 量表简介（必填，支持富文本）：一段介绍文字，会出现在医生端报告中作为量表说明。需支持分段、加粗等基本格式。
- 适用人群（必填，多选）：成人、青少年（13-17 岁）、儿童（6-12 岁）、老年人等标签。
- 预计完成时间（分钟）（必填）：用于提示患者。
- 状态（启用/停用）：停用的量表不会出现在任何推送组合中，但已有数据不受影响。

**量表条目管理**：

在量表编辑页面内嵌一个条目管理子模块。以可排序表格的形式列出该量表的所有条目（题目）。

- 条目字段：题号（自动排序）、题目文本（必填）、选项类型（单选，所有量表统一使用单选）、选项列表、计分规则、反向计分标记、所属维度。
- 「添加条目」按钮：点击后在列表末尾新增一个空条目行，填入题号。
- 支持拖拽排序调整条目顺序。
- 每个条目需要配置：

**选项列表配置**：为每个条目配置选项。选项的数量和文案由量表原版决定。常见的有 4 级选项（如 PHQ-9 的「0=完全没有、1=有几天、2=一半以上天数、3=几乎每天」）或 5 级选项（如 SCL-90 的「1=没有、2=很轻、3=中等、4=偏重、5=严重」）。管理界面提供一个灵活的选项编辑器，允许添加/删除选项行，每行包含：选项显示文本、对应计分数值。注意：选项计分不一定从 0 开始或连续，需要根据量表原版配置。例如 SCL-90 的 5 级评分是 1-5 分。

**计分规则配置**：

- 默认计分：选项对应的分数即为该题得分。
- 反向计分：勾选「反向计分」标记后，该题的实际得分 =（最大可能分数 - 原始选项分数 + 最小可能分数）。例如一个 4 级评分（0-3 分）的题目标记为反向计分，则选择 0 得 3 分，选择 3 得 0 分。系统自动计算。
- 维度归属：每个条目需要指定归属的维度（如 GAD-7 是单维度量表，所有 7 题都属于「焦虑」维度；SCL-90 则需要为每题指定归属的因子维度）。维度名称从该量表预先配置的维度列表中选择。

**量表维度配置**：在条目列表上方，有一个「维度管理」区域。为量表添加维度，如 SCL-90 需要添加 10 个维度（躯体化、强迫症状、人际敏感、抑郁、焦虑、敌对、恐怖、偏执、精神病性、其他）。每个维度包含：维度名称、维度缩写、维度简介。条目配置时从这些维度中选择归属。

**总分/维度分计算规则**：系统默认的计算逻辑为：量表总分 = 所有条目得分之和（自动处理反向计分）；维度得分 = 该维度下所有条目得分之和。这个默认逻辑适用于绝大多数量表。如果个别量表有特殊的计算规则（如需要加权、需要标准化转换等），初期可以先在代码中处理特例，后续通过配置化脚本引擎扩展。MVP 阶段以默认求和逻辑覆盖 95% 的量表需求。

**量表预览功能**：在编辑页面提供一个「预览」按钮，点击后弹出模拟的患者作答界面，展示该量表在患者端实际看到的效果。预览模式不计入真实数据，方便管理员检查题目显示和选项配置是否正确。

**量表复制功能**：支持「复制量表」操作，复制一个新量表（名称需要修改），包含所有条目和配置。这在创建相似量表（如 HADS-A 和 HADS-D 实际上是同一个量表的两个分量表）时非常有用。

## 5.3 常模数据管理

常模是评估个体分数偏离程度的重要参考。常模数据需要支持灵活配置和定期更新。

**常模数据结构**：常模数据按「量表-维度-人群分组」组织。一个量表可以有多个常模版本（如不同年份采集的常模）。每条常模记录包含：

- 所属量表（外键关联）。
- 所属维度（如果是维度常模；总分常模用「总分」标识）。
- 适用人群分组：按年龄段（如 18-25, 26-35, 36-45...）、按性别（男/女/全部）、按其他分层变量（如学生/在职，初期可简化为仅年龄和性别）。
- 样本量（该常模基于多少人的数据）。
- 常模来源（如「中国成人常模，2019 年版」）。
- 描述性统计数据：均值、标准差、各百分位数值（至少包含 P25, P50, P75, P90, P95, P99）、各分级阈值（如正常上限、轻度下限、中度下限、重度下限）。

**常模录入方式**：

- 手动录入：在管理界面逐字段填写。
- 批量导入：支持通过 CSV 或 Excel 文件批量导入常模数据。系统提供标准模板文件下载，管理员按模板整理数据后上传导入。
- 导入校验：导入时校验数据完整性（必填字段、数值范围合理性）、去重检查（同一量表-维度-人群分组的常模只能有一条启用）。

**常模版本管理**：每个常模记录有「启用/停用」状态。同一量表-维度-人群分组只能有一条启用状态的常模。更新常模时，新增一条记录并设为启用，旧的记录自动停用（保留历史数据不删除）。这样可以追溯历史常模的使用情况，也方便必要时回滚。

**常模在报告中的使用**：系统在生成报告时，根据患者的量表得分和常模配置，自动匹配最合适的人群常模（匹配逻辑在计分引擎中实现）。匹配不到时常模对比区域显示「暂无适用常模数据」，不影响其他内容的展示。

## 5.4 分科规则引擎配置

分科规则是本平台的智能核心之一，决定了系统如何根据答题分数给出分科参考标签。

**规则引擎设计思路**：采用「条件-结论」的硬规则模型。条件部分描述量表和分数的组合模式，结论部分输出对应的分科标签。规则引擎在执行时遍历所有启用的规则，对满足条件的规则输出其结论标签。多条规则可以同时触发，输出多个标签。规则评估在报告生成时执行，结果缓存在报告数据中。

**规则配置界面**：

- 规则列表页：展示所有已配置的分科规则。列表字段：规则名称、触发条件摘要、输出标签、状态、操作。
- 新增/编辑规则页面：包含以下配置项：
  - 规则名称（必填）：如「GAD-7 中重度焦虑提示」。
  - 优先级（数字，越小优先级越高）：当多条规则输出的标签有冲突时，高优先级规则的标签优先展示。
  - 触发条件配置（核心部分）：使用可视化的条件构建器。每一行是一个条件子句，多个子句之间是「且（AND）」的关系。如果需要「或（OR）」逻辑，需要配置多条规则。每个条件子句包含：
    - 量表选择（下拉列表，选择已启用的量表）。
    - 维度选择（下拉列表，选择该量表的维度，可选项包含「总分」）。
    - 运算符（大于、大于等于、小于、小于等于、等于、介于）。
    - 阈值（输入数值，如果是「介于」则需要输入两个值：下限和上限）。
  - 示例条件：「GAD-7 总分 >= 15」或「PHQ-9 总分 介于 10 和 19」。
  - 输出标签配置：
    - 医生版标签文本（必填）：面向医生和专业人员的简洁描述，如「焦虑水平中度偏高，建议进一步评估」。
    - 家长版标签文本（必填）：面向家长和非专业用户的详细描述，如「孩子在焦虑相关的自评中得分处于偏高的范围。这不一定意味着孩子有焦虑症，但提示我们孩子的情绪状态需要更多关注。建议您在近期安排孩子与心理科或精神科医生进行一次沟通，由专业人士进行全面评估。您可以拿着这份报告作为参考与医生交流。」
    - 标签颜色/样式（可选）：如蓝色（建议）、黄色（关注）、橙色（需要跟进）、红色（建议尽快就诊）。
    - 适用场景标签（可选，多选）：如「建议精神科就诊」「建议心理咨询」「建议睡眠监测」等。
- 规则启用/停用：支持单条规则的启用和停用，方便调试和临时调整。
- 规则测试功能：提供一个「测试规则」按钮，输入模拟的各量表分数，查看哪些规则会被触发，输出什么标签。这对管理员验证规则配置的合理性非常有用。

**默认规则集**：系统预置一套基础分科规则，覆盖常见的分数模式。这些预置规则作为配置数据随系统初始化导入，管理员可以在此基础上修改和扩充。预置规则的设计需要项目负责人与心理学专业人士讨论确定，但规则引擎的灵活性足以支持任何合理的规则组合。

## 5.5 医生账号管理

管理端需要管理所有医生/家长端的登录账号。

**医生账号列表**：分页表格展示所有医生账号。列表字段：用户名、姓名/机构名（创建时填写的可选信息）、角色、状态、创建时间、最后登录时间、操作按钮。操作按钮：编辑、重置密码、停用/启用、删除。

**创建医生账号**：管理员填写用户名、初始密码、姓名或机构名称（可选）、角色（医生/家长/其他）。创建成功后初始密码显示在页面上，提示管理员将密码安全地告知使用者。密码不在系统中明文存储，显示后即不可再次查看（只能重置）。

**重置密码**：管理员可以为医生账号重置密码。重置后生成新的随机密码并显示，用户下次登录时强制修改。

**停用/启用**：停用的账号无法登录，但该账号已生成的数据保持完整，不影响已关联的报告查看（如果管理员需要查看的话）。这是「软删除」策略——不断绝已有数据关联。

## 5.6 系统配置管理

将平台的一些全局参数集中管理，避免散落在代码或配置文件中。

**配置项列表（可动态扩展）**：

- 患者撤回时限（小时）：默认 24，可调整。
- 作答超时提醒时间（分钟）：默认 30。
- 快筛 PHQ-4 各分支阈值：包括焦虑维度阈值、抑郁维度阈值、总分阈值等（虽然推送规则可以更细粒度配置，但核心阈值放在全局配置中便于快速调整）。
- 患者端结果页文案：包括结束语、鼓励话语库（多条，随机抽取）、调节小贴士库（多条，随机抽取）、联系邀请人提示文案。这些都支持富文本编辑。
- 知情同意书全文：支持版本管理，修改后新患者看到新版本，已签署的保留历史版本。
- 禁用词列表：用于后台录入时的校验提醒（初期可以软校验即警告提示，不强阻止）。

**配置修改**：所有配置项在管理界面以表单形式编辑，修改后立即生效（可缓存，但有缓存刷新机制）。配置修改操作记录到操作日志。

# 第六章 核心机制技术实现

## 6.1 快筛推送决策引擎

推送决策引擎是本平台第一个核心业务引擎。它负责在患者完成 PHQ-4 后，根据分数和其他补充信息决定推送哪个深度包。

**引擎执行流程**：

1. 接收输入参数：PHQ-4 四题的各题得分、焦虑维度分（前 2 题之和）、抑郁维度分（后 2 题之和）、总分、睡眠筛查题答案（如有）、压力筛查题答案（如有）。
2. 从数据库加载当前启用的推送规则集（缓存以减少数据库访问）。
3. 按规则优先级从高到低依次评估每条规则的条件。规则条件结构为：一组 AND 连接的判断子句，每个子句包含（量表/筛查题、维度/题目、运算符、阈值）。
4. 第一个条件完全匹配的规则被采纳，输出该规则对应的量表组合包 ID。
5. 如果没有规则匹配，执行默认分支（推送全面筛查包或状态良好包，取决于总分）。
6. 返回组合包 ID、组合包内量表列表、预计总用时。

**规则配置数据模型**：

```
推送规则表 (push_rules):
- id: 主键
- name: 规则名称
- priority: 优先级（数字越小越优先）
- condition_json: JSON格式的条件定义
  示例：[{"source":"phq4","dimension":"anxiety","op":"gte","value":4},
         {"source":"phq4","dimension":"depression","op":"lt","value":3}]
- package_id: 匹配后推送的量表组合包ID
- status: 启用/停用
- created_at, updated_at: 时间戳
```

**组合包配置**：

```
组合包表 (scale_packages):
- id: 主键
- name: 包名称（如"焦虑深度包"）
- description: 包描述
- estimated_time_minutes: 预计用时
- scale_ids: JSON数组，包含量表ID列表和展示顺序
  示例：[{"scale_id":3,"order":1},{"scale_id":5,"order":2},{"scale_id":7,"order":3}]
- status: 启用/停用
```

**性能考虑**：规则集规模很小（初期不超过 20 条），全量加载到内存缓存，每次测评仅做内存匹配。量表组合包数据同样缓存。整个决策过程在毫秒级完成。

## 6.2 邀请码生成与生命周期管理

**邀请码生成算法**：

```python
import secrets
import string

def generate_invite_code(length=8):
    alphabet = string.ascii_uppercase + string.digits
    # 排除易混淆字符
    exclude = {'0', 'O', '1', 'I', 'L'}
    usable = [c for c in alphabet if c not in exclude]
    return ''.join(secrets.choice(usable) for _ in range(length))
```

使用 `secrets` 模块而非 `random` 模块，确保密码学安全性。8 位字符在排除 5 个易混淆字符后，可用字符集为 31 个，理论组合数为 31^8 ≈ 8.5×10^11，足够防止碰撞和枚举。

**邀请码状态机**：

```
[生成] → 未使用
未使用 → 已填 (患者完成测评)
未使用 → 已过期 (超过有效期，如果配置了有效期)
未使用 → 已作废 (医生手动作废)
已填 → 已阅 (医生打开报告)
已填 → 已撤回 (患者24小时内撤回)
已阅 → 已撤回 (患者24小时内撤回，即使已阅也可撤回)
已撤回 → [终态]
已过期 → [终态]
已作废 → [终态]
```

**数据归属与权限校验**：

- 每份测评数据（作答记录）通过 `invite_code_id` 外键关联到唯一的邀请码。
- 邀请码通过 `creator_id` 外键关联到医生账号。
- 任何需要访问测评数据的接口，后端必须校验：当前登录医生的 ID 是否等于该数据关联邀请码的 `creator_id`。不匹配则返回 403 Forbidden。
- 管理员的权限边界单独定义：初期管理员无权查看医生专属数据（除非有明确的审计需求，后续可通过配置开启）。

## 6.3 计分引擎

计分引擎负责根据量表配置的计分规则，计算各维度的原始分和总分。

**引擎逻辑**：

1. 接收输入：量表 ID、该量表的作答数据（题号:选项分数的映射）。
2. 加载量表配置（条目列表、选项计分、反向计分标记、维度归属）——这些数据从量表库配置中获取，建议缓存。
3. 遍历每个条目：
   - 获取原始选项分数。
   - 如果条目标记为反向计分，执行转换：实际得分 = 最大可能分数 - 原始分数 + 最小可能分数。
   - 将实际得分累加到该条目所属维度的总分中，同时累加到量表总分中。
4. 计算完成后，返回结构化的计分结果：

```json
{
  "scale_id": 3,
  "scale_name": "GAD-7",
  "total_score": 12,
  "max_score": 21,
  "dimension_scores": {
    "anxiety": {"score": 12, "max": 21}
  },
  "item_scores": [
    {"item_number": 1, "raw_score": 2, "final_score": 2, "reversed": false},
    ...
  ]
}
```

**常模对比**：在计分完成后，系统查找适用的常模数据。匹配逻辑：

1. 找到该量表-维度的所有启用常模。
2. 根据患者信息（如果能获取到年龄、性别等基础人口学信息——注意：本平台不采集患者个人信息，因此初版常模对比只能使用「全人群」常模，不分年龄性别。未来如果医生在生成邀请码时可选填患者的基础信息如年龄段和性别，则可以进行更精准的常模匹配）。
3. 返回常模的均值和标准差，以及患者分数在常模中的相对位置（如「高于均值的 1.2 个标准差」）。

## 6.4 分科规则引擎

分科规则引擎在报告生成时运行，输入各量表的计分结果，输出匹配的分科标签。

**引擎执行流程**：

1. 收集患者本次测评的所有量表计分结果。
2. 加载所有启用的分科规则（缓存）。
3. 按优先级从高到低遍历规则：
   - 解析规则的 `condition_json`。
   - 对每个条件子句，从计分结果中找到对应的量表-维度分数。
   - 应用运算符判断条件是否满足。
   - 所有子句都满足时，该规则匹配成功。
4. 收集所有匹配规则的输出标签。
5. 如果存在多条匹配规则，按优先级排序；同优先级按规则 ID 排序。
6. 对所有输出标签进行去重合并（基于标签文本的 MD5）。
7. 返回标签列表，每个标签包含：医生版文本、家长版文本、样式类、适用场景标签。

**引擎的可扩展性**：当前采用 JSON 配置的条件匹配，对于初期需求完全够用。后续如果需要更复杂的逻辑（如支持 OR 条件、支持条件嵌套、支持动态权重计算），可以在不改变接口的情况下升级引擎实现，甚至替换为轻量级规则引擎库。这个架构设计保证了「简约可拓展」。

# 第七章 数据与隐私保护

## 7.1 数据存储原则

**最小化采集**：平台仅采集完成测评所必需的数据。具体来说：知情同意勾选记录（含时间戳和匿名化验证信息）、量表作答的选项选择、提交时间和撤回状态。不采集任何个人身份信息（姓名、手机号、邮箱、身份证号）、不采集生物特征、不采集地理位置、不采集设备指纹。

**数据归属清晰**：每一份测评数据严格绑定到一个邀请码，进而绑定到一个医生账号。数据归属关系在提交时建立，撤回时解除。

**物理隔离**：不同医生的数据在逻辑上通过邀请码-医生 ID 的关联实现隔离。在单数据库部署模式下，这是通过应用层的权限校验实现的。如果未来迁移到多租户数据库架构（每个医生独立数据库），隔离级别可提升到物理层。当前单库方案已满足初期需求，权限校验由后端统一中间件保证，不存在数据泄露风险。

## 7.2 数据加密方案

**传输加密**：全站启用 HTTPS。使用 Let's Encrypt 免费证书，设置自动续期。所有 API 通信均在 TLS 加密信道中进行。

**存储加密**：SQLite 数据库文件存储在服务器本地磁盘。鉴于当前部署形式为笔记本单机，数据库文件本身依赖操作系统文件系统权限保护。敏感字段（如有）使用 AES-256 进行字段级加密，加密密钥存储在环境变量或独立的密钥文件中，不写入代码仓库。初期需要加密的字段实际上很少（因为不采集个人信息），但加密基础设施需要预留。

**备份加密**：手动备份到移动硬盘时，备份文件使用 gpg 或 zip 加密压缩，密码由管理员保管。自动化备份方案（后续迭代）需包含加密传输到远程存储的能力。

## 7.3 撤回机制的数据删除

数据撤回时执行的是数据库 DELETE 操作，从表中物理移除记录。这不是软删除（设置 deleted_at 标记），而是真正的数据清除。在设计数据表时需要考虑到这一点：作答记录表与邀请码表通过外键关联，删除时使用事务确保一致性。

撤回后不可恢复。这个特性需要在系统设计文档中明确标注，避免开发人员因为「习惯」而使用软删除。同时也需要在操作日志中记录撤回事件（仅记录操作本身，不保留数据副本）。

## 7.4 访问控制与审计

**API 权限中间件**：所有需要登录的 API 端点，通过统一的认证中间件验证 JWT token 的有效性。token 过期返回 401，权限不足返回 403。中间件在请求上下文中注入当前用户信息（user_id, role），后续业务逻辑基于此进行权限判断。

**数据访问日志**：关键操作记录操作日志，包括：医生查看报告（记录查看者 ID、报告对应的邀请码、查看时间）、数据导出（记录导出者 ID、导出格式、导出时间）、管理员修改量表配置（记录修改者 ID、修改内容摘要、修改时间）。操作日志存储为结构化数据，支持后续查询和审计。日志保留期建议不少于 6 个月。

**安全事件响应**：如果发现未授权访问迹象（如短时间内大量报告查看操作、异常 IP 登录尝试），系统应有基本的告警能力。初期可以通过日志监控脚本实现，后续可接入专业监控工具。

# 第九章 技术架构详细设计

## 9.1 技术选型说明

**后端框架：Python Flask**

选择理由：轻量级、灵活、学习曲线平缓，极其适合单人开发和快速迭代。Flask 的扩展生态可以按需添加功能（如 Flask-SQLAlchemy 用于数据库 ORM、Flask-JWT 用于认证、Flask-CORS 用于跨域支持），不会像 Django 那样携带大量初期不需要的功能。Python 生态在数据处理方面有明显优势（计分引擎、规则引擎的实现会更简洁）。

**数据库：SQLite（初期）/ PostgreSQL（后续）**

选择理由：SQLite 零配置、零运维，文件型数据库直接存储在笔记本硬盘上，非常适合单机部署场景。Flask-SQLAlchemy 作为 ORM 层可以无缝切换数据库后端，当需要迁移到 PostgreSQL 时，只需修改数据库连接字符串，几乎不需要改动业务代码。SQLite 的并发能力对于初期用户量（医生数量在几十人以内、患者测评请求稀疏）完全够用。

**前端-患者端：原生 HTML/CSS/JavaScript + 轻量级 UI 框架**

选择理由：患者端功能相对简单（表单填写+结果展示），使用原生技术或极轻量框架（如 Alpine.js + Tailwind CSS）可以做到极小的打包体积和快速的加载速度。这对于移动端网络环境不稳定的场景非常重要。不使用 React/Vue 等重型框架，保持页面简洁和性能优秀。

**前端-医生端/管理端：React 或 Vue + 组件库**

选择理由：医生端和管理端有较为复杂的交互（邀请码管理表格、报告富文本展示、量表编辑器、规则配置器等），使用现代前端框架可以显著提升开发效率和用户体验。组件库推荐使用 Ant Design（React）或 Element Plus（Vue），提供了表格、表单、弹窗等后台管理常用组件。医生端需要响应式设计以支持手机查看报告。

**部署方案：笔记本 + DDNS + Nginx 反向代理**

选择理由：最低成本的部署方案。使用一台 7×24 小时开机的笔记本电脑（建议配置：8GB 以上内存、SSD 硬盘、稳定供电），安装 Linux 系统（Ubuntu Server LTS 推荐）。通过 DDNS 服务（如花生壳、Cloudflare DDNS）将动态 IP 映射到固定域名。使用 Nginx 作为反向代理和静态文件服务器，Gunicorn 或 uWSGI 作为 Flask 应用的 WSGI 服务器。HTTPS 通过 Let's Encrypt 的 certbot 自动管理。这个方案的总成本：域名费（约 50 元/年）+ 电费（约 100-200 元/年）+ DDNS 服务费（可能有，约 100-200 元/年）。全年运营成本可控制在 500 元以内。

# 第十章 非诊断原则的技术落地

## 10.1 四层兜底机制的代码实现

四层兜底是本平台最重要的合规设计，每一层都需要在代码中有明确的实现点和不可绕过的校验。

**第一层：知情同意书强制确认**

- 实现位置：患者端知情同意页面 + 后端 consent 接口。
- 不可绕过保证：患者只有在调用 POST /api/v1/patient/consent 接口成功后才能调用任何答题相关接口。后端在每个答题接口的会话校验逻辑中，检查 `assessment_sessions.consent_given` 字段是否为 true。如果为 false，拒绝请求并返回错误码 CONSENT_REQUIRED。
- 追加保护：知情同意的勾选不是前端按钮的简单 enable/disable，而是必须通过接口提交，后端记录不可篡改的时间戳和验证哈希。

**第二层：答题前弹窗提醒**

- 实现位置：患者端，在快筛完成后、深度包开始前。
- 内容：固定的「请确认您将认真、真实地作答」弹窗，用户必须点击确认才能继续。
- 后端配合：弹窗确认事件记录到会话日志中（audit_logs 表），作为用户被提醒过的证据。

**第三层：结果页固定灰字免责声明**

- 实现位置：患者端结果页 + 医生端报告页。
- 硬编码保证：免责声明文案不从配置表读取，而是直接写在前端组件代码和后端报告生成逻辑中。这是有意为之——防止管理员误操作或未来商业化压力下修改或弱化这些声明。
- 文案内容（见 3.6 节和 4.3 节）包含四条固定声明和全国心理援助热线。
- 样式要求：患者端显示为灰色小字但可读（字号不小于 12px，对比度符合 WCAG AA 标准），医生端报告显示为明显但不过分干扰的提示框。

**第四层：全站通用的状态描述语**

- 实现位置：所有自动生成的结果文本。
- 禁用词过滤：在分科规则引擎的输出端、以及所有可能动态生成文本的位置，增加一个文本过滤函数 `sanitize_output(text)`。该函数维护一个禁用词列表（存储在配置中，但过滤逻辑硬编码确保执行），对输出文本进行匹配检查。如果检测到禁用词，自动替换为对应的安全表述，并记录警告日志（以便管理员发现配置不当的规则）。
- 动态性声明：每份报告的固定位置添加「本结果仅反映您近期的心理状态倾向」、「心理健康是动态的」、「不代表诊断」等声明，这些是硬编码插入的，不依赖任何配置。

以下为系统内置的默认禁用词及替换表述表。该表存储在数据库配置表中，但核心替换逻辑在代码中实现，即使配置表为空也会执行硬编码的基础替换。

## 10.3 结果分步展示的实现

- 报告默认展示区域首先呈现「当前状态描述」——仅包含各量表得分的文字描述和常模对比位置，不包含任何分科建议标签。
- 状态描述区域下方有一个设计克制的按钮：「查看分科参考建议」。

## 11.3 风险应对预案

| 风险场景 | 应对措施 |
|---|---|
| 版权方要求下架 | 管理后台可立即停用指定量表，停用后该量表不再出现在任何推送组合和新测评中。已有数据保留但标记量表状态为「已下架」，报告查看时在量表名称旁标注「该量表已停止使用」。 |
| 数据被不当解读 | 四层兜底机制+分步展示+固定免责是防线。如发生纠纷，系统可调取知情同意记录和操作日志，证明用户被充分告知平台性质和数据用途。 |
| 服务器宕机 | 笔记本长期运行的风险通过以下方式降低：使用稳定性较好的操作系统（Ubuntu Server LTS），配置自动重启脚本（systemd service 设置 Restart=always），定期检查硬件健康状态。备用方案：准备一个随时可以替换的备用机，数据通过定时备份可以快速迁移。 |
| 数据丢失 | 建立严格的备份制度：每日凌晨自动备份数据库文件到本地另一个目录；每周手动备份到移动硬盘；每月备份到云端存储（如加密后上传到网盘）。备份保留最近 30 天的每日备份。恢复演练每季度进行一次。 |
| 用户量意外增长 | 初期架构的瓶颈在 SQLite 的并发写入。当同时测评的用户数超过 SQLite 的并发处理能力（通常约 10-20 个并发写入）时，切换为 PostgreSQL。由于使用 SQLAlchemy ORM，切换仅需修改数据库连接字符串和少量 SQL 方言差异。在达到瓶颈前，通常有足够的时间进行平滑迁移。 |

# 第十三章 非功能性需求详细说明

## 13.1 性能要求

**响应时间目标**：

- 患者端页面首次加载（含所有静态资源）< 3 秒（3G 网络环境）。
- API 接口响应时间：简单查询（邀请码验证）< 200ms，复杂查询（报告生成）< 2 秒，数据导出（PDF/Excel 生成）< 10 秒。
- 快筛推送决策 < 100ms。

**并发能力**：

- 初期支持 10 个并发测评会话（患者同时在线答题）。
- 医生端支持 20 个并发医生同时查看报告。
- SQLite 在 5-10 个并发写入时表现良好，超过此阈值时考虑迁移 PostgreSQL。

**数据量预估**：

- 每个测评会话平均产生 100-300 条作答记录（取决于推送的量表组合）。
- 假设初期有 10 位医生，每位每月发出 50 个邀请码，其中 30 个被使用，则月增测评会话 300 个，作答记录 3-9 万条。
- SQLite 单表百万级数据量仍可良好运行，按此增速足够使用 2-3 年。

## 13.2 可用性要求

- 服务可用时间：7×24 小时（笔记本持续运行）。允许每月不超过 2 小时的计划内维护窗口。
- 移动端兼容性：
  - 患者端必须完美适配移动端（iOS Safari 最新两个版本，Android Chrome 最新两个版本，微信内置浏览器）。
  - 医生端报告查看在移动端需基本可用（表格可横向滚动，文字可读）。
- 浏览器兼容性：
  - 患者端：支持主流浏览器的最新两个版本。
  - 医生端/管理端：支持 Chrome、Firefox、Edge 最新两个版本。不考虑 IE11 兼容。

## 13.3 安全性要求

- 身份认证：JWT token 过期时间 24 小时，刷新机制可选实现。密码强度要求：长度 ≥8 位，包含字母和数字。密码存储使用 bcrypt（cost factor ≥ 10）。
- 传输安全：全站 HTTPS，HTTP 请求自动 301 重定向到 HTTPS。HSTS 头部设置（max-age=31536000，可选）。
- 数据验证：所有用户输入在后端进行严格校验和净化。SQL 查询统一使用 ORM 的参数化查询，防止 SQL 注入。前端输出进行 HTML 实体编码，防止 XSS 攻击。
- 权限控制：每个涉及数据访问的 API 端点都必须进行权限校验，不允许通过修改 URL 参数访问其他医生的数据。权限校验逻辑集中在中间件和服务层，不在前端做任何权限假设。

## 13.4 可维护性要求

- 代码规范：后端遵循 PEP 8 Python 代码规范。前端遵循 ESLint 标准配置。使用 Prettier 进行代码格式化。提交前必须通过代码规范检查。
- 日志规范：使用结构化日志（JSON 格式或标准日志格式），包含时间戳、日志级别、模块名称、消息内容。错误日志必须包含堆栈信息。关键业务操作记录 INFO 级别日志（如邀请码生成、测评提交、报告查看、数据撤回、配置修改）。
- 配置管理：敏感配置（数据库密码、JWT 密钥、加密密钥）通过环境变量注入，不写入代码或配置文件。其他配置集中在数据库配置表或配置文件中，但以数据库配置表为优先，支持运行时修改。
- 文档要求：API 接口必须有文档（至少包含端点路径、请求方法、参数说明、响应示例）。核心业务逻辑函数必须有注释说明其用途、输入输出。数据库表结构变更必须记录在迁移脚本的注释中。

## 13.5 可扩展性要求

- 数据库扩展：ORM 层使用 SQLAlchemy，切换数据库后端仅需修改连接字符串和少量方言差异。表结构设计使用迁移脚本管理，支持版本化升级和回滚。
- 量表扩展：新增量表通过管理后台操作，不需要修改代码。新量表的计分逻辑如果在「求和」范式内，完全配置化；特殊计分逻辑需要代码支持（预留扩展点）。
- 规则引擎扩展：分科规则和推送规则均通过配置管理，支持运行时增删改。后续可替换为专业规则引擎（如 Drools、JsonRules 等），接口保持兼容。
- AI 融合扩展：预留 `ai_service.py` 服务模块，定义 `generate_interpretation(score_data, rule_tags) -> str` 接口。首版返回空或默认文本，迭代 2 接入 DeepSeek API 时仅需修改该模块的实现，业务代码无需变动。

# 第十四章 测试策略

## 14.1 测试分层

## 14.2 测试数据管理

使用测试专用数据库，不与生产数据库共用。测试数据使用 fixture 或 factory 模式生成，确保测试的可重复性。敏感测试场景（如撤回后数据删除验证）使用独立的事务，测试后自动回滚。
