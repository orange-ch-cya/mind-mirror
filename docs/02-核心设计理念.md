# 第二章 核心设计理念详解

## 2.1 简约可拓展原则的落地要求

简约不是简陋，可拓展不是预留一堆用不上的抽象层。本项目中「简约可拓展」的具体实现要求如下：

**数据库层面**：核心业务表结构保持稳定，但所有配置类数据（量表条目、计分规则、常模数据、分科规则）必须存储在数据库表中而非硬编码在代码中。新增或修改一个量表不应要求开发人员介入，管理员通过后台界面即可完成。数据库版本控制采用迁移脚本管理，所有 DDL 变更必须可追溯、可回滚。

**API 层面**：所有接口路径以 `/api/v1/` 为前缀，为后续版本升级预留空间。接口设计遵循 RESTful 规范，请求和响应格式统一使用 JSON。每个接口的响应结构包含统一的 `code`、`message`、`data` 三个顶层字段，便于前端统一处理。错误码体系独立于 HTTP 状态码，业务错误统一返回 HTTP 200，通过 `code` 字段区分业务结果。

**前端层面**：组件设计遵循原子设计方法论。基础 UI 组件（按钮、输入框、弹窗、卡片等）作为原子组件独立封装；业务组件（量表答题组件、报告展示组件、邀请码管理组件等）组合原子组件构建；页面级组件承载完整的业务场景。任何组件的修改不应影响其他无关组件。

**配置层面**：所有可变参数（快筛阈值、推送规则、常模数据、分科标签映射、免责声明文案、禁用词列表等）均需实现后台可配置。配置文件或配置表的结构要支持热更新，修改配置后无需重启服务即可生效。

## 2.2 以患者为中心原则的落地要求

「以患者为中心」在本项目中不是一句口号，而是有明确实现标准的工程原则：

**知情权保障**：患者在开始答题前，必须阅读并主动勾选知情同意书。知情同意书的内容必须清晰告知：本平台的性质（非医疗工具）、数据去向（邀请码持有者可见）、患者自身的权限（无法自行查看详细报告）、撤回权利（24 小时内可撤回）。知情同意的勾选记录作为数据归属的追溯凭证永久保存。

**隐私保护**：患者端不采集任何个人身份信息。不要求输入姓名、手机号、邮箱、身份证号等可识别字段。不采集 GPS 定位。不读取设备信息。不埋设第三方跟踪脚本。邀请码是关联患者数据的唯一标识，而邀请码本身由医生生成和管理，与患者个人身份无直接映射关系。

**情绪安全**：患者看到的结果页不显示任何分数、量表名称、倾向性词汇、科室建议。仅显示温和的结束语、通用性的鼓励话语、普适性的心理调节小贴士、固定的免责声明、以及「请联系邀请您参与测评的人士获取进一步解读」的提示。整个体验应该让患者感觉「完成了一件有意义的事」，而非「被贴上了一个标签」。

**撤回权保障**：患者在提交测评后的 24 小时内，拥有无条件撤回数据的权利。撤回操作将导致其测评数据从数据库中彻底删除，关联的邀请码同步作废。撤回功能在患者端结果页提供明确的入口，操作步骤简单明了，不需要任何审批流程。

**不伤害底线**：平台全链路杜绝标签效应。禁用词表内置在系统中，不仅约束前端显示文案，也约束后台配置时的录入校验。凡是可能让患者产生「我被诊断为 XX」联想的表述，一律替换为客观状态描述。这一要求在结果生成逻辑中以硬编码校验层实现，不依赖人工遵守。

## 2.3 双重读者适配原则的落地要求

医生/家长端的报告呈现面临一个核心矛盾：专业用户需要精确的数据，非专业用户需要能理解的解读。解决方案是分层呈现：

**数据层**：所有读者看到相同的原始数据。包括逐题作答记录、各量表原始分数、与常模的对比数据、分科参考标签。这层数据保持客观、完整、不修饰。

**解读层**：为专业数据配发通俗注释。例如在「GAD-7 总分 12 分」旁边显示注释「该分数处于中度焦虑范围（常模参考：0-4 分正常，5-9 分轻度，10-14 分中度，15-21 分重度）」。注释文案由专业人士预先编写，存储在配置库中，系统根据分数区间自动匹配，不依赖 AI 实时生成。

**建议层**：分科标签使用双轨描述。面向医生的描述可以简洁专业（如「建议精神科进一步评估」），面向家长的描述需要更多上下文（如「孩子的情绪状态显示出一些需要关注的特征，建议您带孩子前往医院的临床心理科或精神科，由医生进行全面评估。这个建议不意味着孩子一定有问题，只是表明目前的状态值得专业人士的关注。」）。两套描述在配置中成对存储，报告展示时根据查看者角色自动选择，或者同时显示并以标签区分。
